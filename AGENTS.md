## Layer Boundaries

Five layers, hexagonal dependency direction: **Core → Adapters → Features → Composition Root → App**.

| Layer             | Folder                                                              | Knows about                              | Does NOT know about                   |
| ------------------ | -------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------- |
| Core               | `internal/core/` (+ `core/tooldef`)                                   | Domain types, all ports (`ModelPort`, `ToolPort`, `ContextPort`), extension/hook contracts (`Extensions`, hooks, `Decision`), the loop/FSM/turn/events, the `core.Agent` contract, the tool authoring contract (`tooldef.Definition`, `ExecutionContext`, `Schema`) | Everything else — adapters, features, harness, app |
| Adapters           | `internal/adapters/` (`agent`, `contextstore`, `eventbus`, `toolport`) | Core only; concrete implementations of core ports — `agent` implements `core.Agent`, `contextstore` implements `ContextPort`, `eventbus` implements `Emitter` (+ `Hooks` dispatch), `toolport` implements `ToolPort` (`Composite`/`Wrap`) plus the native `Registry` | Features, harness, app |
| Features           | `internal/features/<name>/` (plus `subagent.SpawnExt`, which lives in `harness/subagent` — see exception below) | Core only (+ `core/tooldef`); each package colocates its implementation with its `core.Extension` registration in `ext.go` | Other features, adapters, harness internals |
| Composition root   | `internal/harness/` (`harness.go`, `harness_options.go`, `memory.go`, `context_files.go`, `gate.go`; `runner/` facade; `subagent/` as a child composition root; `prompttmpl/` slash-command templates; `session/` persistence) | Everything below: builds adapters, the default + caller extension set, the composite ToolPort, assembles the system prompt, wires one runner per loop | Tool implementations' internals       |
| App                | `api/` (HTTP/SSE server + `turnqueue`/`sse`/`approvals`/`costs`/`ui` subpackages), `internal/app/` (`nexus/`, `modelregistry/`, `wsclient/`), `cmd/app/`          | Harness's public surface (`RunTurn`, `WithTool` registration) | —                                      |

**Never import upward.** Core imports nothing from `internal/` — it does import `pkg/common` for canonical message/tool types (`ProviderToolDefinition = common.ToolDefinition`), which is a boundary crossing to the shared type package, not an internal layering violation. `internal/` never imports `pkg/providers` or `pkg/models` except `internal/app/modelregistry`, the composition root's provider-construction helper — the app-side piece of the caller's job, alongside library consumers building their own clients. Adapters import core, never features or harness. Features import core only. Agent (`internal/adapters/agent`) doesn't import runner. If you need cross-layer communication, use an interface injected via config.

Two deliberate exceptions to "never import upward":

1. `harness.New` imports `internal/adapters/agent` in exactly one place — the unexported `defaultAgentBuilder` fallback — so a harness works out of the box with no brain injection. All other harness code talks only to the `core.Agent` interface. Callers with a custom brain override it via `harness.WithAgentBuilder(builder)`.
2. `internal/harness/subagent` is a **child composition root**: it deliberately imports both `internal/features/*` (to share the skills/blackboard extensions and assemble a child's extension set) and `internal/harness/runner` (to build the child's `AgentRunner`) — the same wiring job `harness.go` does for the main agent, done again per spawn.

### Blackboard REPL

The blackboard is strictly an agent→subagent communication mechanism: one-shot subagents deposit their findings before disconnecting, and the parent inspects them. It is not designed for long-lived agents to share results — contents are in-memory only and lost on any reset.

`internal/features/blackboard/` hosts the sandboxed Python REPL subprocess machinery (`repl.go`, `bootstrap.py`) plus the `Querier` interface and its LLM-backed implementation (`querier.go`) — the model-facing `rlm` tool and its offload path have been removed — alongside the `Blackboard` that builds on it: one persistent REPL per harness, shared by the main agent and all subagents through the `repl` tool. A single mutex serializes all access; write-own-slot is enforced in code — `bb` is a guard dict and creating/replacing a top-level key other than the executing agent's slot raises `PermissionError` (reads are unrestricted; the trusted Go `Deposit` path bypasses the guard). The blackboard's namespace (`bb` guard dict, `peek`, `bb_grep`) is injected via a setup exec (no blackboard-specific logic in `bootstrap.py`); `bootstrap.py`'s only related feature is a transport-level stdout cap (100k chars).

Known limit: `llm_query` inside the blackboard holds the REPL lock for all agents while it runs; keep individual calls small and prefer `llm_batch` for fan-out work. If this hurts, the upgrade path is an async callback queue — don't reach for it speculatively.

Cancellation or transport failure mid-call resets the blackboard (contents lost, lazily restarted empty); agents must tolerate missing slots.

Registration is via `internal/features/blackboard/ext.go` (package `blackboard`): a `core.Extension` providing the `repl` tool (`core.ToolProvider`, wrapping the same REPL tool implementation) and closing the blackboard on `core.SessionEndHook` (run by `Harness.Shutdown` with a 5s timeout). The `*blackboard.Blackboard` is built at the composition root and shared — main gets `blackboard.NewExt(bb, "main")`, each subagent gets `NewExt(bb, childID)`. Behavior unchanged.

## Adding Tools

All tools reach the model through the composite ToolPort (`internal/adapters/toolport/composite.go`), which mounts three source kinds in stable definition order: native registry tools (sorted by name), extension `core.ToolProvider` bundles (registration order), then `core.DynamicToolSource` snapshots (re-read at each turn's `BeginTurn`). Name collisions with an already-mounted tool are a construction error (dynamic collisions are skipped with a warning). The loop snapshots the port once per turn and passes the definitions into every `DoReasoning` call — the agent holds no tool state.

Two ways to add a tool:

**File-edit diffs:** `Edit` and `Write` return a unified diff of the change. `internal/features/builtins/diff.go` (`DiffFiles`, backed by `github.com/pmezard/go-difflib`) produces a `Diff{Text, Added, Removed, Omitted}`; the model sees only the counts appended to the result (`Edit applied. +3 -1`) while the body rides in `ToolResult.Metadata` (`diff`, `diff_added`, `diff_removed`, `diff_omitted`) so it costs no tokens. Three size rules: a diff over `maxDiffLines` (50) is dropped body-and-all with `Omitted: "too large"`; a file over `maxDiffFileLines` (20000) is never diffed at all (`"file too large"` — difflib's matcher is O(n*m)); binary content (existing `isBinary`) yields `"binary"`. `maxInlineDiffLines` (20) is advisory, consumed by the UI via `Diff.Inline()` to decide expanded vs click-to-expand — mirrored as `INLINE_DIFF_LINES` in `api/ui/index.go`. `Metadata` reaches drivers through `ToolSucceededEvent.Metadata` → wire's `toolSucceeded.metadata` (additive + `omitempty`, so no `wire.Version` bump) → SSE. `PreviewDiff(workingDir, toolName, arguments)` computes the same diff for a call that has NOT run yet, backing the approval preview; it shares `applyEdit` with the Edit tool so preview and reality cannot drift. It never writes — a stale preview (file changed since) is cosmetic, since `FileTracker.Verify` still guards the real edit.

1. **Native built-in** (file/shell-level tooling): create `internal/features/builtins/tool_<name>.go`, implement `tooldef.Definition` (`Name()`, `Description()`, `Schema()`, `Execute()`, from `internal/core/tooldef`), and add it to `builtins.Defaults()` — the composition root seeds every `toolport.NewRegistry` with that set — or inject via `harness.WithTool`.
2. **Extension tool**: implement `core.ToolProvider` on an extension — return `core.ToolSpec`s carrying their own `Execute` closure and an `Origin` like `"extension:<name>"`. No registry registration needed.

Notes:

- Tool descriptions are **instructions to the model**, not documentation — precise wording controls tool selection
- Tools never throw. Errors return `ToolResult{IsError: true}`; panics are recovered into error results by `Composite.Execute`. Loop doesn't break on tool errors
- Tools that perform no mutations should implement `tooldef.ReadOnlyReporter` (`ReadOnly() bool` → true; extension tools set `ToolSpec.ReadOnly`) — the loop runs consecutive read-only calls in a batch concurrently (bounded at 8), while unmarked tools act as barriers and run alone. The same marker gates `WithReadOnly` mode (unmarked tools are denied there). When in doubt, leave a tool unmarked

If the tool needs external state (skill registry, task graph), define a narrow interface in tooldef and accept it in the constructor. Don't import the concrete type.

## Adding Skills

1. Create `<skills-dir>/<name>/SKILL.md` with YAML frontmatter (default skills dir is `~/.claude/skills`; add more with `harness.WithSkillsDir`):
   ```yaml
   ---
   name: skill-name
   description: What the skill does and when to use it (full YAML — multi-line/folded values supported; `name` is required, `description` optional)
   ---
   ```
2. Body is loaded lazily via `load_skill` tool — no registration code needed
3. Skill metadata is discovered at startup from frontmatter only. Skills are keyed by the **directory** name, matching Claude Code; the frontmatter `name` is still required and validated but does not name the skill, and a mismatch logs `slog.Warn` naming both. Frontmatter YAML rejects (typically an unquoted `description` containing `": "`, which YAML reads as a nested mapping) fall back to a line scrape of `name`/`description` (`scrapeFrontmatter`) rather than dropping the skill; a directory with no `SKILL.md` is skipped silently, any other discovery failure logs `slog.Warn`
4. `runServe` prints the loaded skills in the startup banner (`printSkills`, `cmd/app/container.go`), sourced from `harness.Skills()` — the same name→description index the agent sees
5. **Plugin skills (default-on):** Claude Code plugins contribute skills too (`internal/features/skills/plugins.go`, `harness.WithPluginsDir`, default `~/.claude`). A plugin dir is a *Claude config* dir — the one holding `settings.json` and `plugins/` — not a skills dir. Discovery: `settings.json`'s `enabledPlugins["<plugin>@<marketplace>"]` must be `true`; the install root comes from `plugins/installed_plugins.json` (`plugins[key][].installPath`, first non-empty wins); `<root>/.claude-plugin/plugin.json` supplies the namespace (its `name`, falling back to the key's `<plugin>` half) and, when it declares `skills: [...]`, an authoritative allowlist of skill dirs — otherwise `<root>/skills` is walked **recursively**, since plugins nest skills under category folders. Registered as `"<namespace>:<dir>"`, so plugin skills never collide with standalone ones or each other. Every step is best-effort: missing or malformed metadata yields no plugins, never a startup failure, so the harness still runs where Claude Code is not installed

UX unchanged; new plumbing: skills surface through `internal/features/skills/ext.go` (package `skills`) — a `core.Extension` providing the `list_skills`/`load_skill` tools (`core.ToolProvider`) and the "Available skills…" system-prompt index (`core.PromptContributor`, appended by the composition root). The agent knows nothing about skills. The same extension instance is shared with subagents via the factory config (read-only registry).

## MCP Servers

`harness.WithMCPServer(mcp.ServerConfig{Name, Command, Args, Env})` (repeat per server; re-exported as `tenzing.WithMCPServer`/`tenzing.MCPServerConfig`) mounts an external MCP server over stdio. The `mcp` extension (`internal/features/mcp`) connects on session start (a dead server logs a warning and serves zero tools — deliberately NOT load-bearing), closes on session end, and implements `core.DynamicToolSource`: tools are re-listed at each turn's `BeginTurn` with a 30s cache and surface as `mcp__<server>__<tool>` with `Origin: "mcp:<server>"`. Trust: the default permission policy's `AskOrigins: ["mcp:"]` escalates every MCP-origin tool to approval unless its full name is explicitly allow-listed. SSE/HTTP transports and `listChanged` subscriptions are follow-ons.

## Providers

The provider layer lives in this repo (no external LLM module):

- `pkg/common` — canonical types used throughout the harness: `common.LLM` (the client interface, including `GetModel() Model`), `Model`/`ModelDefinition`, `CompletionRequest`/`CompletionResponse`, `Message`, `ContentBlock`, `ToolDefinition`, streaming/stop-reason types, sentinel errors.
- `pkg/providers/protocols/` — protocol clients, each `NewClient(model Model, opts...) (common.LLM, error)`: `anthropic` (native SDK), `ollama` (native `/api/*` endpoints; diagnostics go to the default `slog` logger at Debug level), and `openai_compat` (OpenAI-compatible APIs — OpenAI, OpenRouter, or any compatible endpoint — via `WithBaseURL`/`WithAPIKey`; tool-call arguments are normalized to valid JSON on both ingestion and replay — empty → `{}`, malformed → wrapped under `"_raw"` — because compat providers like Ollama Cloud 400 on replayed tool calls with unparseable arguments). API keys and base URLs are the caller's job — pass them via client options (`WithAPIKey`); nothing reads env vars in `pkg/`. Every protocol retries server 429s with exponential backoff by default (`ratelimit.NewDefaultBackoff` values; streaming retries only while no events have been emitted) — `WithRetryBackoff(ratelimit.RetryBackoff)` overrides the values, zero fields keep their defaults. Every protocol also takes the same two limiting options, off by default: `WithRateLimit(rate, burstSize)` (API token bucket; both values must be set or `NewClient` errors) and `WithMaxConcurrency(n)` (in-flight bound — inside the token bucket when combined with `WithRateLimit`, a pure semaphore alone) — `NewClient` wraps internally with `ratelimit.Wrap`, so callers never wrap themselves.
- `pkg/providers/protocols/ratelimit/` — `Limiter` primitives (`TokenBucket`, `Semaphore`), the `Wrap` decorator, `RetryBackoff`, and the shared 429 retry helpers (`IsRateLimited`, `Backoff`, `RetryOnRateLimit`, `RetryStreaming`) used by every protocol client. Internal plumbing for the protocol options; callers only touch `TokenBucketConfig` and `RetryBackoff`.
- `pkg/models` — convenience catalog of standard `common.Model` definitions (provider-prefixed vars; `models.Standard()` returns all as `[]ModelDefinition`). Convenience only, never a hard requirement: any `common.Model` implementation works with the protocol clients. **`cmd/app` does not read it** — the CLI's models come solely from tenzing.yaml — so it exists for library consumers, and a model added there does not appear in the CLI.

Models are `common.Model` values (`common.ModelDefinition{Name, MaxTokens, ContextWindowSize, DefaultContextWindow, Provider, SupportsThinking, SupportsVision}`), not strings. `Provider` is a plain string field ("anthropic", "ollama", ...) — pure metadata; there is no `Provider` type and nothing in the library dispatches on it. The harness never constructs clients — callers build a `common.LLM` from a protocol package and inject it. `internal/app/modelregistry` is the app-side factory package: `Factory.Get(rm ResolvedModel)` switches on the model's **provider type** → protocol constructor, taking the endpoint and key from the model's own `config.Provider` entry. There are only three types — `anthropic`, `ollama`, `openai_compat` — because those are the three protocols the repo implements; vendor names are not types: every hosted OpenAI-compatible API is `openai_compat` plus its own `url`, which is why that is the default when a provider names no type. There is no env-var fallback for keys. `url` is required for `openai_compat` (the URL is the only thing identifying the backend) and optional for the other two, whose clients carry their vendor's endpoint. The compat client is named after the provider's **name**, not its type, so several compat backends stay distinguishable in logs. A provider's `extra:` map becomes `WithExtraField` calls applied in sorted key order (map iteration is random, the client stores extras as an ordered slice); the reserved `max_completion_tokens` key becomes `WithMaxCompletionTokens` instead, since it renames a parameter rather than adding a field. `extra` is ignored on anthropic/ollama. The per-run `Factory` cache is keyed (provider **name**, wire model name, reasoning effort), so two models of the same type behind different endpoints never share a client, and per-provider extras need no extra key component.

## Constructing a Harness

`harness.New(mainLLM common.LLM, opts ...HarnessOption) (*Harness, error)` is the harness constructor — the caller builds the client (protocol package + model) and injects it. External consumers use the public facade `pkg/tenzing` — pure type/func aliases over `internal/harness` (plus the `runner`, `tooldef`, `core`, and `adapters/eventbus` types its options reference) exposing `tenzing.New` + `Harness.RunTurn` for a single programmatic loop. The LLM type layer is NOT re-exported — consumers import `pkg/common` (types) and `pkg/models` (standard definitions) directly; `pkg/tenzing` aliases only the harness surface. New harness options and Hooks event types must be re-exported in `tenzing.go` in the same change; new standard models go in `pkg/models`, which serves library consumers only — the CLI resolves models from tenzing.yaml and never consults it. The brain defaults to the built-in agent implementation (`internal/adapters/agent`); override with `WithAgentBuilder`.

`HarnessConfig` no longer exists. Behavior is configured via flat `HarnessOption` functions (`internal/harness/harness_options.go`):

- `WithAgentBuilder` — replaces the default agent implementation with a custom `runner.AgentBuilder` (the test seam for stub brains).
- `WithSubagentLLM` / `WithBlackboardLLM` / `WithAdvisorLLM` — per-role `common.LLM` clients. Unset subagent/blackboard roles fall back to the main LLM. `WithAdvisorLLM` has no fallback — it is the opt-in switch for the advisor feature: when set, the transcript-aware `advisor` tool (automatically sees the main conversation via the context store; takes one optional `question` argument) and its write-gate extension (`advisor.GateExt`, `internal/features/advisor/ext.go`) are both registered. The gate denies each turn's first state-changing tool call until `advisor` has been consulted (read-only tools flow freely; unknown/MCP tools count as state-changing; max 20 consults per turn), and denies plan checkpoints — `TodoWrite`, `TodoCreate`, `TodoUpdate` with `status: done` — unless `advisor` was called with no state-changing calls since (`writesSinceConsult`; todo tools never count as writes, so `in_progress` flips flow freely; a capped advisor call still clears the debt so the plan tools cannot deadlock). It contributes the advisor prompt guidance as a `PromptFragment`; the advisor's own system prompt states this cadence and asks it to name an earlier milestone when one is warranted. `WithAdvisorNudge(n)` / `--advisor-nudge n` additionally reminds an unconsulted executor from iteration n onward (default off). `WithAdvisorExemptTools(names...)` names tools the gate never blocks even unconsulted — for a harness whose only state-changing action is a forced/schema-only answer tool with no orientation phase to precede it, where denying costs a deny→advisor→retry round-trip the harness has no budget for. Unset = no advisor tool, no gate, no prompt fragment.
- `WithTool` — injects an additional tool implementing `tooldef.Definition` (used by cmd/app to register nexus channel tools).
- Subagents (`spawn_agent` tool) are enabled by default at depth 1 using the main model; `WithSubagentDepth(0)` disables the tool.
- The shared blackboard REPL is **always on** (no disable option — the Python process boots lazily on first use): main agent and subagents share one persistent Python process (`repl` tool); subagent results over 2000 chars are deposited to `bb['<agent_id>']['result']` and returned as a 1500/500-char head/tail preview. Blackboard execs/deposits are logged via `slog` at info level (code capped 500 chars, stdout head 200).
- `WithPromptTemplatesDir(dir)` — registers a directory of `*.md` slash-command templates (repeatable); a `RunTurn` query of the form `/name args...` is expanded with bash-style argument substitution (`$1..$9`, `$@`/`$ARGUMENTS`, `${N:-default}`, `${@:N:L}`) before the loop sees it; an unknown `/name` fails the turn without an LLM call (`internal/harness/prompttmpl`).
- **Context files (default-on):** the globals `<UserConfigDir>/tenzing/AGENTS.md`, `~/.claude/CLAUDE.md` and `~/.claude/rules/*.md` (globbed directly — Claude Code auto-discovers that directory rather than importing it, so there is no `@`-import chain to follow; `filepath.Glob` returns sorted matches, keeping the prompt byte-stable), plus every `AGENTS.md` and `CLAUDE.md` from the filesystem root down to cwd (`contextFileNames` sets the within-directory order: `AGENTS.md` then `CLAUDE.md`), are appended to the main system prompt (path headers, `contextFilesMaxBytes` 128KB cap; `internal/harness/context_files.go`). A line that is exactly `@path` is an import: it is replaced in place by that file's content (resolved against the importing file's directory; `~/` and absolute paths honored), recursively to `maxImportDepth` (5). A `seen` set is both the cycle guard and cross-candidate de-duplication, so no file is inlined twice; an import that is missing or already loaded is left as the literal `@path` line rather than blanked. Main agent only — subagents keep their focused prompts. Opt out with `WithContextFilesDisabled()`. `loadContextFiles` returns a `contextLoad`: the prompt text, the context-file paths actually read (imports included), the rule-file paths tracked separately, and whether the cap was hit; `harness.ContextFiles()` / `harness.RuleFiles()` expose them and `runServe` lists each in its own startup-banner section (`printContextFiles` / `printRuleFiles`, `cmd/app/container.go`) — rules are standing policy rather than project context, so they are counted apart, though they share the context files' opt-out and print nothing when it is set, which prints `context disabled (--no-context-files)` instead of a count when the flag is set, so "opted out" is distinguishable from "none found", and appends `(truncated — tail dropped)` when `harness.ContextFilesTruncated()` reports the cap was hit — every path is still listed, but the tail of the last file(s) never reached the prompt.
- `WithToolCallGate(gate)` — installs a pre-execution veto (`func(ctx, core.ToolCall) error`) consulted before every tool call, main agent and all subagents (one shared gate, implemented as a `core.Extension` ToolCallHook registered right after permissions). A non-nil error blocks the call; the error string is fed back to the model as the tool result.
- `WithBudgets(budgets.Limits{MaxIterations, MaxWallClock, MaxTokens})` — graceful per-turn termination (`terminated: <reason>` error from `RunTurn`); zero fields unlimited. Subagents get `MaxIterations` from `WithSubagentMaxIterations` (default 100) via the same extension.
- `WithMCPServer(cfg)` — mounts an external MCP server (see "MCP Servers" above); repeat per server.
- **Permissions (default-on):** the permissions extension gates tool calls by name — the default policy (`permissions.DefaultPolicy`) escalates code-executing/file-writing tools (`bash`, `write`, `edit`, `repl`, `spawn_agent`) to `AskUser` (`advisor` is deliberately not listed: it is read-only and the advisor write-gate mandates calling it, which must not hang on approval in headless mode); the loop then emits `ApprovalRequestedEvent` and blocks up to `WithApprovalTimeout` (default 120s; 0 = deny immediately) for a `Respond(bool)`. Override the policy with `WithPermissionPolicy` — tenzing.yaml's `permissions:` section (`allow`/`deny`/`ask`/`ask_origins`) reaches it through `permissionPolicy` in `cmd/app/permissionpolicy.go`, which merges the lists into `DefaultPolicy` and removes each named tool from the other two lists so a configured `allow` outranks a default `ask`. `Policy.Bash` (`internal/features/permissions/bash.go`) then refines the name-level decision for the `bash` tool by parsing and classifying the command itself. The parser is `internal/features/permissions/shell` (pure — no `core` import — built on `mvdan.cc/sh/v3/syntax`, Bash dialect): `shell.Analyze(command, table)` returns one `Segment` per simple command the line runs — top level, inside `$(…)`/backticks/`<(…)` (`Depth` +1), inside compound commands (`for`/`if`/`{ }`/`( )`/functions), and spliced in from a literal `bash -c '…'`/`sh -c`/`eval` script (`Depth` +1, capped at 4 levels). Each segment has `Text` (the statement printed by mvdan's printer WITHOUT its leading `NAME=value` assignments, single-line, whitespace-normalised, backticks rewritten to `$(…)`, redirects kept as `>f` with no space), `Raw` (WITH assignments), a static `Argv` (quoted words unescaped; `$VAR`/`$(…)`/globs are non-static), and a `Class` bitset: `read` (empty), `fs:write`, `fs:delete`, `net`, `vcs`, `unknown`. Classification: wrappers (`sudo`, `env`, `xargs`, `find -exec`, `timeout`, `nice`, `nohup`, `time`, `command`, `exec`) classify by their inner command (the `Text` stays the full `sudo rm x`, so an `rm *` glob does NOT cover it — write `sudo rm *`); `ssh`/`docker exec`/`kubectl exec` are `net` and are not recursed into; output redirects to anything but `/dev/null`/`/dev/std*`/`/dev/fd/*`/a descriptor add `fs:write`; everything else is looked up in `shell.Builtin()` (`table.go`, keys `bin`, `bin sub`, `bin sub sub2`, `bin -flag`, `bin sub -flag`; flag hits replace the bin/sub class so `sed -i` writes and `unzip -l` reads; short clusters expand per character, erring toward mutation) plus a few argument-shape specials (`git branch/tag/stash/remote/worktree/config`, `tar`, `tee`, `awk` — read unless the program text contains `>` or `system(`, `rsync`). Build/test tools (`go build/test/vet`, `cargo build`, `tsc --noEmit`) are `read` by decision (their cache/bin output is their own workspace); interpreters (`python`, `node`, `perl -e`), `npx`, `make`, `docker run`, `./anything`, `$CMD` and any binary not in the table are `unknown`. A parse error yields `Analysis.Err`; a command that runs nothing (assignments only) yields no segments. `BashRules` is a concurrency-safe value (`NewBashRules`/`Lists`/`SessionList`/`Categories`/`Classify`/`AllowPattern`/`AllowPatternSession`/`Analyze`/`Verdict`, `UnmarshalJSON` for the settings file; the lists are copy-on-write so the hook can match while an approval driver appends). `Verdict(command) (Decision, reason, ok)` decides in this fixed order: a parse error → `AskUser` with the error as reason, after matching the deny globs against the whole raw string (an unbalanced quote must not hide `rm -rf /` from an `*rm -rf*` deny); no segments → no verdict; any segment whose `Raw` or `Text` matches a `deny` glob → `Deny` (so an env prefix cannot bypass a deny and a rule can target the assignment itself, `LD_PRELOAD=*`); segments matching an `allow` glob (persisted or session) are covered and exempt from category rules — EXCEPT that a glob covers the binary it names, never a redirect bolted onto it: `cat *` does not cover `cat > f` or `cat > f <<EOF` (that would allowlist writing any file through any read-only binary); a redirect write is covered only by a glob that spells the redirect (`cat >*`, `rm * >*`) or by `fs:write` in `categories.allow`, while descriptor dups and `/dev/null` discards are not writes and stay covered by the binary glob; any uncovered segment with a class bit in `categories.deny` → `Deny`; an uncovered segment is covered when every class bit is in `categories.allow` — which `read` (no bits) always is, and `unknown` never can be; every segment covered → `Allow`; otherwise `AskUser` with `Analysis.Summary()` as the reason (one line per mutating segment: class, text, why — this is what the approval UI shows). `matchGlob`: `*` spans any bytes including `/`, `?` one byte, case-sensitive; not `path.Match`; a glob ending in ` *` also matches the argument-less command. A name-level `deny` of `bash` is absolute and no command glob can override it. Net effect: a fully read-only command (`grep x f | head`, `go build ./... 2>&1 | tail`) runs with no prompt and no rule; anything that mutates or is unknown prompts until a glob or category covers it. `internal/features/permissions/corpus_test.go` pins this against the 23 commands from one real session: 22 auto-allow, the one `npx` prompts and converges on a single suggested rule. The bash tool itself runs `bash -c` (`internal/features/builtins/tool_bash.go`), so parser and executor agree; there is no zsh dialect in mvdan, and zsh-only syntax hits the parse-error path. These rules come from `settings.json`, not tenzing.yaml (see Setting precedence below) — opt out entirely with `WithPermissionsDisabled()`, or auto-approve with `WithDangerouslySkipPermissions()` (CLI `--dangerously-skip-permissions`) — that mode keeps every hook in place but resolves any `AskUser` decision in the main loop to `Allow` without emitting an approval request (`Deny` still denies; for Docker sandboxes / CI pipelines with nobody to answer prompts; implemented as `LoopConfig.SkipPermissions`). `WithReadOnly()` (CLI `--read-only`) is the unattended-safe mode: it REPLACES the permissions extension with a hook in `internal/harness/readonly.go` (shared with subagent loops) that denies every call whose tool is not marked read-only per `Composite.ReadOnly` (unmarked/unknown = mutating; `write`, `edit` deny) — except `bash`, which runs when `shell.Analyze` against the built-in table only (no `settings.json` overrides in the unattended mode) classifies every segment `read`; a mutation, an unknown binary, a parse error or an assignment-only command is denied with the analysis summary as the reason — no AskUser escalation exists in this mode (`WithPermissionPolicy` is ignored, MCP tools' own read-only claims are trusted) and the approval timeout is forced to 0, so no prompt or timeout ever fires. Exemptions: `advisor` is marked read-only (pure LLM call); `repl` is marked read-only (its sandbox blocks file writes — only shared in-memory blackboard state mutates); `spawn_agent` is allowed by name because child loops carry the same gate — spawned agents cannot touch the filesystem, only shared in-memory blackboard state. Ordering guarantee: permissions run FIRST among extensions, and later hooks can escalate but never lower its decision. **Migration note:** consumers driving the harness headlessly (no `OnApprovalRequested` hook, no cmd/app UI) must either call `WithPermissionsDisabled()` or handle the approval event — otherwise mutating tools are denied after the approval timeout. Subagent loops carry no permissions extension (the parent's spawn was already approved).
- `WithThinking(enabled)` — toggles model reasoning for the main agent's requests (default: provider default). Runtime toggle: `Harness.SetThinking` (between turns; emits `ThinkingChangedEvent`).
- `WithThinkingBudget(tokens)` / `--thinking-budget N` / tenzing.yaml `thinking_budget:` — caps reasoning tokens per main-agent LLM call by setting `CompletionRequest.ThinkingBudget` (main agent only; subagent/blackboard/advisor roles get none). Exact on Anthropic (`budget_tokens`; a budget with `Think` nil enables thinking on the wire), tiered to `reasoning_effort` on OpenAI-compatible and mapped to a `think` level on Ollama (same `<4096`/`<16384` cutoffs). The budget beats a model entry's `reasoning_effort` (warned once at construction); an explicit `WithThinking(false)` leaves it inert; the agent clamps it to `maxTokensStdResponse - 1024` (warned) since Anthropic requires it below the request's `max_tokens`. No runtime setter yet — `SetThinking` covers the on/off axis.
- `WithLLMRetry(max, baseDelay)` — tunes the default agent's transient-LLM-error retry policy (default 3 retries / 2s base, exponential backoff + jitter; negative max disables). Network errors, timeouts, and 5xx/429/overload retry; 4xx does not; a streaming call that already emitted deltas is never retried. Each retry emits `LLMRetryEvent`.
- `WithCompressionThreshold(frac)` / `WithCompressionKeepMessages(n)` — tune the main context store's auto-compression (defaults 0.75 of context window / 6 messages kept).
- **Runtime controls (between turns only; `errBusy` mid-turn):** `Harness.Compact(ctx, instructions)` forces context compression via the context store (works with any brain); `Harness.SetLLM(llm)` switches the main agent to a caller-built client and emits `ModelChangedEvent` (`CurrentModel()` reads back the active `common.Model` via `llm.GetModel()`; client reuse/caching is the caller's job — cmd/app's `Factory` cache makes switch-back free); `Harness.SetThinking(bool)` toggles reasoning and emits `ThinkingChangedEvent`; `Harness.Clear()` drops the history (`contextstore.Store.Clear`) and rotates to a new session record, and `Harness.Resume(conversationID)` loads a persisted conversation over the live one (`Store.Replace` + todo list + thinking preference). Both rotate via `rotateSession`, which moves only the on-disk conversation identity — `ConversationID()` follows it, while the runner ID (the event-stream identity, which the session persister filters on) is fixed for the harness's life. SetLLM/SetThinking require the default brain (custom `WithAgentBuilder` brains get a clean error unless they implement `SetLLM`/`SetThinking`).
- **Prompt caching:** every default-agent request sets `CacheSystemAndTools` (Anthropic caches system prompt + tool schemas; other providers ignore it); cache token counts surface on `LLMResponseEvent` (`cache_read_input_tokens`/`cache_creation_input_tokens`).
- `WithConversationID(id)` — resumes a prior conversation: the main agent runs under `id` instead of a random one. When session persistence is on (the default), `harness.New` loads that conversation's latest session JSONL file (same cwd), reconstructing message-level history into the main `contextstore.Store`'s `InitialHistory` (tool outputs capped at 4KB on replay; compaction entries restart the replay from their summary plus the most recent reconstructed messages) and restoring the todo plan from the latest snapshot entry; the compression-summary memory file remains the fallback (seeded as `InitialMemory`) for conversations without a session file. Omit to start a new conversation under a random ID (`Harness.ConversationID()` returns it either way — the caller's handle for a future resume).
- **Session persistence (default-on):** `internal/harness/session/` — a persister subscribed to the event bus appends main-agent events as JSONL entries to `<UserConfigDir>/tenzing/sessions/<cwd-hash>/<timestamp>_<conversationID>.jsonl` (header line, then user / assistant / tool_result / steering / compaction / todo-snapshot entries with an `id`+`parent_id` chain; images go to content-addressed sidecar blobs). Append-only and best-effort: a write failure logs a warning and disables the store for the process; subagent events are filtered out. `WithSessionDisabled()` opts out, `WithSessionDir(dir)` relocates; `Harness.SessionInfo()` reports the resolved dir + cwd; `session.List/Delete/Rename` manage files.

The harness holds no LLM cache — it uses exactly the clients injected via `New`/`With*LLM`/`SetLLM`. cmd/app caches clients per (provider, model, reasoning effort) in `internal/app/modelregistry`'s `Factory` so roles sharing a model share one client.

Memory (`internal/harness/memory.go`) is separate from the in-process `contextstore.Store`: it's the harness's own `ContextCompressedEvent` subscriber, persisting each compaction's summary to a per-conversation file (`.agent_memory-<stamp>-<runnerID>.md`, main-agent files in the OS config dir, subagent files in the OS cache dir) so a later `WithConversationID` resume — even in a new process — has something to load. Neither `internal/core` nor `internal/adapters/contextstore` know this file-backed store exists; they only emit/consume the event.

## CLI (`cmd/app`)

`cmd/app` is a single cobra command, `tenzing` (`cmd/app/root.go`), with three modes: no `-p/--prompt` → serves the HTTP/SSE app (`runServe`, `NewAppContainer`); with `-p "prompt"` → one headless agent turn then exit (`cmd/app/print.go`): `--output-format text` (default, final answer only) or `json` (JSONL — every harness event plus text/thinking deltas, with a `{"type":"result",...}` line guaranteed last, written only after the event bus is closed and drained); with `--connect <url>` (or `connect:` in tenzing.yaml) → **control-plane mode** (`cmd/app/connect.go`): the process dials the control plane's WebSocket server, registers with `hello`, and executes turns from plane commands while streaming `wire.Envelope` events back over the same connection — no HTTP listener, no embedded UI, no nexus. The normative protocol contract is `docs/adrs/2026-09-12-control-plane-fleet/PROTOCOL.md` (protocol version "1"); the client lives in `internal/app/wsclient` (dial with bearer token, read/write pumps, jittered exponential backoff with a 30s cap, reconnects forever). The load-bearing lifecycle rule: **a dropped connection cancels the in-flight turn** — each turn's context derives from the connection's, so socket loss aborts the turn via the loop's clean "turn canceled" path (`internal/core/loop.go`), the turn's outcome classifies as `cancelled_disconnect` and is reported in the next `hello`'s `last_turn` (the disconnect is authoritative; the result is advisory), and the wiring's event forwarder stops forwarding once no turn is running (backlog discard). Explicit `cancel` commands cancel the turn context WITHOUT touching the connection watcher, so they classify as `cancelled`. A serial queue (`connectSerialQueue` in `connect.go`) gives one-turn-at-a-time with FIFO follow-ups; `cancel` and disconnect both flush waiters (they report `cancelled` — never carried across a reconnect). Approvals are first-class push: `ApprovalRequestedEvent` responders are captured into an `approvals.Registry` (the `api/events.go` pattern) and answered by `approve` commands on the same socket. Mode dispatch in RunE: print > connect > serve, mutually exclusive (`--connect` + `-p` is an error); serve-only flags warn-and-ignored in connect mode. Connect config: `--connect` > env `TENZING_CONNECT` > tenzing.yaml `connect:` (`internal/config.ConnectSection{url, token, backoff}`); `--connect-token` / `TENZING_CONNECT_TOKEN` carry the bearer token; `--connect-backoff` (default 1s) sets the reconnect base. The JSONL schema is the versioned wire contract in `internal/app/wire`: every line is an `Envelope` (`v`, `type`, `ts`, `runner_id`, typed `data` payload), core and nexus events are explicitly mapped (durations converted to real milliseconds — core's `duration_ms` tags marshal nanoseconds), unmapped events become `unknown_event` lines instead of leaking core struct shapes, and any breaking payload change requires a `wire.Version` bump. The serve-mode SSE stream builds its payloads from the same envelopes (`sse.Translate` in `api/sse/translate.go`, adding a top-level `agent` label; the embedded UI in `api/ui/index.go` parses those shapes), and connect mode forwards the same envelopes over the WebSocket. Exit codes: `0` success, `1` config/startup error, `2` turn failure. Headless permission default is `WithApprovalTimeout(0)` (deny mutating tools immediately) unless `--approval-timeout` was explicitly passed or `--no-permissions` is set (connect mode also exempts `--dangerously-skip-permissions`); denied calls emit `core.ToolDeniedEvent` (`tool.denied`), print mode counts them and reports a stderr summary plus a `denied_tools` field on the json result line — exit code stays 0. Event delivery is lossless under stdout backpressure: an unbounded in-memory queue (`eventQueue` in `cmd/app/print.go`) sits between the 256-slot bus subscription and the stdout writer — the drain side never blocks, so the bus's drop-on-full `Emit` never fires for a slow consumer. A *failed* stdout write (consumer closed the pipe) cancels the in-flight turn — no tokens are burned streaming into a void. An explicitly empty prompt (`-p ""`) is a config error, not serve mode.

The root command has one subcommand: `tenzing init` (`cmd/app/init.go`) copies the embedded starter files (`cmd/app/defaults/` — `tenzing.yaml`, `settings.json`, `SYSTEM_PROMPT.md`, embedded as `defaultFiles embed.FS`) into `userConfigDir()`, skipping any that already exist so a re-run never clobbers a config holding API keys. Note `.gitignore`'s bare `tenzing.yaml` rule needs the `!cmd/app/defaults/tenzing.yaml` negation or the embed breaks on a fresh clone. Everything else is flags on the root command: ~28 flags parse into `cliConfig` (`cmd/app/options.go`); `--config` (default `./tenzing.yaml`, falling back to `<UserConfigDir>/tenzing/tenzing.yaml`; env `TENZING_CONFIG`) loads the unified config file whose values fill flags-and-env-left-unset fields (`internal/config` schema + `mergeConfigFile` in `cmd/app/configmerge.go`; MCP servers from the file land pre-parsed in `cfg.MCPServerConfigs`, additive with `--mcp-server`; a `permissions:` section lands as `cfg.PermissionPolicy`, which has no flag equivalent); `--settings` (default `./settings.json`, falling back to `<UserConfigDir>/tenzing/settings.json`; env `TENZING_SETTINGS`) loads per-command bash globs that layer onto that policy as `PermissionPolicy.Bash` (`cmd/app/settingsfile.go`); `harnessOptions(cfg)` maps the resolved config to the same `HarnessOption`s for both modes — model flags (`--model`, `--subagent-model`, `--blackboard-model`, `--advisor-model`, resolved via `cfg.deps`, see below), budgets (`--max-turn-tokens`, `--max-iterations`, `--max-wall-clock`), toggles (`--advisor-nudge` (warned + ignored without `--advisor-model`), `--subagent-depth`, `--approval-timeout`, `--no-permissions`, `--dangerously-skip-permissions`, `--read-only`, `--thinking`, `--thinking-budget` (0 = provider default), `--no-session`, `--no-context-files`), prompt/session/trust flags (`--system` file replacing the system prompt, `--resume <id>`, `-c/--continue` for the latest session — mutually exclusive with `--resume`, requires persistence — `--trust` one-shot trust grant, `--timeout` print-mode turn deadline), wiring (`--mcp-server` repeatable, `--conversation-id`, `--provider` repeatable JSON provider definitions merged over the file's `providers:` by name), and serve-only flags (`--port`, `--nexus-config`) — passing those with `-p` (or in connect mode) prints a stderr warning and they are otherwise ignored (as is `--timeout` without `-p`). Connect-mode flags: `--connect <ws-url>` (env `TENZING_CONFIG`-style chain: flag > env `TENZING_CONNECT` > tenzing.yaml `connect:`), `--connect-token` (env `TENZING_CONNECT_TOKEN`), `--connect-backoff` (duration, default 1s). Print prompts may carry `@path.png`-style tokens (png/jpg/jpeg/gif/webp) that attach the files as images via `RunTurnWithImages`. `--debug` is shared by both modes — it never touches stdout, but it does raise the log file to trace level and switch it to a fresh timestamped filename (`setupLogging`), in print mode same as serve mode, and in serve mode it also un-collapses the embedded UI (`ui.Handler` in `api/ui/ui.go` substitutes it into `api/ui/index.go`'s `DEBUG` constant: off → thinking renders as a live `✻ Thinking for <d>…` line (`fmtDuration`, ticking every 100ms) over a rolling 3-row window onto the tail of the reasoning text (`.msg.thinking .preview`: `max-height` of three rows, `overflow: hidden`, scrolled to the bottom on each delta, so the browser does the wrapping and the newest rows show), settling to `✻ Thought for <d>` with the reasoning text dropped when the block ends; a block ends at the next text delta, tool call, answer, or turn end, so a turn with three thinking stretches shows three separately-timed lines. Tool calls render as `⏺ name(input)` plus a `⎿` outcome line showing up to the first 3 non-blank output lines (each clipped to 80 chars) and a `+ N lines` tail when there are more, with no progress detail; on → full thinking text (no timer, no window, retained after the block ends), full input, and the first 10 output lines). Both modes log to `<UserConfigDir>/tenzing/log/` (`logDir` in `cmd/app/print.go`, temp-dir fallback). `--subagent-depth`, `--approval-timeout`, and `--thinking` have unset-vs-zero semantics (0/false are valid explicit values), so `markSetFlags` records cobra's `Changed()` into `cfg.SubagentDepthSet`/`ApprovalTimeoutSet`/`ThinkingSet`.

Setting precedence: explicit flag > env var > tenzing.yaml > default. `mergeEnv` (`root.go`) applies the three pre-existing env vars (`SERVER_PORT`, `LOG_DEBUG`, `NEXUS_CONFIG`) plus the connect env vars (`TENZING_CONNECT`, `TENZING_CONNECT_TOKEN`, `TENZING_CONNECT_EPHEMERAL_GRANTS`); `mergeConfigFile` (`cmd/app/configmerge.go`) then fills whatever flags and env left unset from the config file — `internal/config` owns the tenzing.yaml schema (`config.File`, strict parsing, unknown keys are startup errors; `$VAR`/`${VAR}` in the file are expanded from the environment before decoding — `expandEnv`, unset references left literal; scalars whose zero is meaningful are pointers so the merge can set the `*Set` markers; the `connect:` section (`ConnectSection{url, token, backoff}`) lands pre-parsed in `cfg.ConnectURL`/`ConnectToken`/`ConnectBackoff`). The file is located via `--config` > `TENZING_CONFIG` > `./tenzing.yaml` > `<UserConfigDir>/tenzing/tenzing.yaml` (`resolveConfigPath`; `userConfigDir` in `configmerge.go` wraps `os.UserConfigDir()` — `~/Library/Application Support/tenzing` on macOS, `$XDG_CONFIG_HOME/tenzing` or `~/.config/tenzing` elsewhere — and is the one place that per-user directory is defined); the two probed paths are optional (missing is fine), missing at an explicit path errors. `resolveFilePaths` (`configmerge.go`) then rebases the file's path-valued keys (`system_file`, `nexus_config`, `mcp_servers[].command`) onto the config file's directory before the merge — absolute paths and separator-free MCP commands (PATH lookups) are left alone, and the corresponding CLI flags stay cwd-relative. `settings.json` is resolved and loaded separately (`cmd/app/settingsfile.go`), after `mergeConfigFile`: `--settings` > `TENZING_SETTINGS` > `./settings.json` > `<UserConfigDir>/tenzing/settings.json` (the same `userConfigDir()` the tenzing.yaml chain probes, so both per-user files sit beside `trust.json`, `AGENTS.md` and `sessions/`) — same explicit-vs-probed rule as the config file (absent probed path = no rules, absent explicit path = startup error), except that a file which exists but is malformed JSON is always a hard error, never a silent skip. Its shape is `{"permissions": {"<tool>": {"allow": [...], "deny": [...], "categories": {"allow": [...], "deny": [...]}, "classify": {"<key>": "<class>"}}}}` — `allow`/`deny` are command globs, `categories` name classes (`read`, `fs:write`, `fs:delete`, `net`, `vcs`; `unknown` is rejected), and `classify` overrides the built-in command table with the same `bin` / `bin sub` / `bin sub sub2` / `bin -flag` keys and comma-joined class values (`"mytool deploy": "net,fs:write"`); files with only `allow`/`deny` still load. Only the `bash` tool is honoured (the only tool whose input is a command line), and other tool keys and other top-level keys are ignored. Tool names are matched case-insensitively throughout — the `permissions` key (`app.LookupTool` in `internal/app/bashallow.go`), the name-level match that applies the command rules (`Ext.OnToolCall`), `/approve` and `/suggest`'s pending-call check, and the UI's `isBash` test — so a `"Bash"` key and a tool registered as `Bash` behave exactly like `bash`. A rewrite of the file keeps whichever spelling the key already used rather than adding a second entry differing only in case. Note the name collision: this `permissions` maps a TOOL to command globs, while tenzing.yaml's `permissions:` section gates tools BY NAME — they are different mechanisms that compose (name-level first, then command-level). `applyBashRules` attaches the rules to `cfg.PermissionPolicy`, creating one from `permissions.DefaultPolicy()` when tenzing.yaml named no `permissions:` section, and always allocates a (possibly empty) `BashRules` plus a `cfg.BashAllow` store (`app.NewBashAllowStore`, `internal/app/bashallow.go`) pointing at the resolved path — so the "allow always" answer works even when no settings file exists yet. **Approval diff preview:** `POST /preview {call_id}` (`handlePreview` in `api/approvals.go`) returns the diff a pending `Edit`/`Write` approval would produce, so the decision is made against the change rather than the raw arguments. The pending-approval map keys the call's `input` alongside the responder and tool name to make this possible. Read-only: the request stays pending either way, and a call that cannot be previewed (wrong tool, unreadable file, `old_string` not found) reports the reason in `error` instead of failing the request. The UI fetches it when an `Edit`/`Write` approval arrives and renders it below the prompt; a failed fetch is swallowed so a preview problem never blocks the decision.

**"Allow always" / "allow for session" (serve and connect modes — print mode has no approver):** both answers add an allow glob to the live `BashRules`; only "always" also persists it. In connect mode an `approve.glob` goes through `connectApprove` (`cmd/app/connect.go`): `BashRules.AllowPatternSession` (in memory only) when `--connect-ephemeral-grants` is true (the default — per-node grants die with the process) OR the command carries `scope: "session"`, else `BashAllowStore.Add` to settings.json. In serve mode the approval UI renders the approval's `reason` (the shell analysis summary) under the command and shows `allow always` and `allow for session` buttons plus an editable glob for `bash` calls, prefilled by `suggestGlob` in `api/ui/index.go` with the command's first word + ` *` and then refined by `POST /suggest {call_id}` (`handleSuggest` in `api/approvals.go`), which returns `{glob, reason}` from `(*BashRules).Suggest` (`internal/features/permissions/suggest.go`). `Suggest` runs the same analysis and proposes a rule for the FIRST segment that would still prompt — not glob-covered, not `read`, not category-allowed — so a chained command converges one rule per approval, and read-only segments (`cd`, `grep`, `head`) never get a rule. The glob keeps a subcommand for binaries where it decides what runs (`git commit *`, `go get *`, `npx ng *` — `subcommandTools`, which also lists the wrappers so `sudo rm -rf x` proposes `sudo rm *`) or a distinguishing leading flag where that does (`sed -i *` — `flagSensitiveTools`), else it is the binary + ` *`. A segment whose write comes from a `>`/`>>`/`&>` redirect or a `tee` gets NO glob and a reason instead (a binary glob would not cover the redirect anyway, and a `tee *` glob would allowlist writing anywhere); a non-static command word (`$CMD`) and a parse error get a reason too. Read-only and advisory — the request stays pending, the field is editable, and a failed fetch leaves the local prefill standing. The UI posts `/approve` with `allow` (implies `approved`) and `scope` (`always` default, or `session`). `handleApprove` (`api/approvals.go`) rejects a blank glob, an unknown scope, one aimed at a non-`bash` call (the pending-approval map keys tool name alongside the responder), or one with no store configured; otherwise `grantAllow` either calls `AllowPatternSession` (status `allowed_session`) or `app.BashAllowStore.Add` (`internal/app/bashallow.go`, status `allowed`), which persists to the resolved settings file FIRST — rewriting only `permissions.bash` (`allow`, `deny`, `categories`, `classify`; `Lists()` excludes session grants so they never reach disk), so other tools under `permissions` and unknown top-level keys survive, creating the file when absent — then calls `AllowPattern` so the rule takes effect for the rest of the session. A failed write leaves the request pending and the live rules untouched, so the user can retry or fall back to a plain approve.

One further env-only setting loads via the same `Config` struct: `TENZING_PROJECT_TRUST` (default `skip`). Main-model precedence is just `--model` flag > tenzing.yaml `model:` — there is no third source, and no model at all is a startup error. A missing config file is likewise fatal (`run 'tenzing init'`): providers and models are declared, never compiled in.

`NewAppContainer(cfg *cliConfig)` builds the HTTP/SSE app from the resolved `cliConfig` — trust resolution + drop-in project config (`internal/app/trust.go`, `cmd/app/projectconfig.go`: SYSTEM.md/APPEND_SYSTEM.md/.tenzing/prompts; project beats global, replace beats append, project-local sources trust-gated, explicit `--system` wins), then the same `harnessOptions(cfg)` print mode uses, plus nexus wiring and the port/nexus-config serve-only fields (`--debug` is shared, not serve-only — see above). The HTTP layer lives in the top-level `api` package and its subpackages `api/turnqueue`, `api/sse`, `api/approvals`, `api/costs`, `api/ui` (see `api/AGENTS.md`) and is dependency-injected through consumer-side interfaces: the container calls `api.New(api.ServerConfig{...})` first (bus, log broadcaster, nexus, trigger flush hook, pricing, `ResolveLLM`/`ModelNames` closures over the registry and LLM cache, the bash-allow store, cwd, trust default, debug — the optional `Nexus`/`BashAllow` interface fields are left unset rather than assigned a nil pointer), builds the harness with `srv.TextDelta`/`srv.ThinkingDelta` as its delta handlers, then `srv.Attach(h)`. The container owns the harness and bus lifecycles; `srv.Shutdown` only closes the turn queue (cancelling the in-flight turn), ends SSE streams, and stops the listener. The registry's tenzing.yaml pricing feeds the server's `costs.Tracker` (`api/costs`; `GET /stats` + `cost` SSE event). `GET /state` also reports `context_window` — `contextWindow()` in `api/turns.go`, the model's `GetDefaultContextWindow()` if set, else `GetContextWindowSize()`, 0 when unknown — which backs the UI status bar's context gauge, plus `cwd`/`home` for shortening tool-call paths in the UI. The embedded UI dispatches slash commands client-side (`COMMANDS`/`parseCommand` in `api/ui/index.go`): `/clear`, `/compact`, `/cost`, `/model`, `/thinking`, `/sessions`, `/resume`, `/help` map to these endpoints and never reach the agent, while an unrecognised `/name` is posted to `/query` unchanged so the harness's own `prompttmpl` templates still resolve.

Model resolution: `internal/app/modelregistry` is a registry built from tenzing.yaml's two top-level lists — `providers:` (`name` label, `type` protocol, required `url`, optional `api_key`) and `models:` (`name` alias, `provider` ref, `model_name` wire id, plus context_window/max_response_tokens/vision/reasoning_effort/cost). `modelregistry.Build(providers, entries)` is pure, no I/O; `root.go` loads the file, merges `--provider` flags over its provider list by name (`modelregistry.MergeProviderFlags`), then builds one `deps` pair (`cmd/app/deps.go`: registry + client `Factory`, parked on `cfg.deps`) before any resolution — there are no process globals. Refs are the **alias**, not `provider/name`: `deps.resolve`/`Registry.List`/`--list-models` look up `byName`. A ref starting with `{` is instead an inline definition — stringified JSON with the `config.ModelEntry` fields, naming a provider that must already be declared — accepted by every model flag. Each resolved model carries its `config.Provider` (`modelregistry.ResolvedModel`), which is what `Factory.Get` builds the client from. `modelregistry` is also where the config spelling `max_response_tokens` becomes the library's `common.ModelDefinition.MaxTokens` — the two limits are named apart in the config (a turn budget vs. one response) but `pkg/` keeps the shorter name, so a grep for the config key stops at that seam.

The **alias/wire-name split matters**: `common.ModelDefinition.Name` holds `model_name` (what protocol clients send and what comes back on `LLMResponseEvent.Model`); the alias never leaves the registry. Pricing is therefore keyed by lowercase `model_name`, not the alias — keying it by the alias silently produces null costs. An entry's `reasoning_effort` rides on `common.ModelDefinition` into `modelregistry`'s client factory, which translates it per provider — `openai_compat.WithReasoningEffort` (`reasoning_effort`) or `ollama.WithReasoningEffort` (the `think` level string); on both, a request `ThinkingBudget` (from `--thinking-budget`) takes precedence and an explicit `Think: false` beats everything; Anthropic takes a numeric budget instead and logs a warning. The value is passed through verbatim, so the provider owns the valid set (Ollama's includes `max`), and it is part of the client cache key, letting inline refs name the same model at different tiers.

Serve mode's `api.Server` queues concurrent queries instead of rejecting them (`turnqueue.Queue`, `api/turnqueue`): `/query` returns `started` or `queued` (FIFO, drained in order by `finishTurn` chaining; `/cancel` drops the queue), and exposes `/steer`, `/state`, `/sessions` (GET/DELETE/PATCH), `/messages`, `/clear`, `/resume`, `/compact`, `/thinking`, `/model`, `/models`, `/stats`, and `/trust` (GET/POST) alongside the pre-existing routes — see `SYSTEM_ARCHITECTURE.md` §16 for the endpoint table.

## Configuration & DI

All non-invariant runner behavior flows through `runner.AgentRunnerOption` functional options (`internal/harness/runner/agent_runner.go`), passed to `runner.NewAgentRunner(agent, opts...)`. To change runner behavior:

- Swap the Agent (different model/provider)
- Swap the ToolRegistry (`WithToolRegistry`, different native tool set) or the whole ToolPort (`WithToolPort` — the harness passes the composite here; unset falls back to wrapping the registry)
- Swap the ContextStore (`WithContextStore`) — required; the `core.ContextPort` implementation that owns this runner's conversation history
- Swap the SystemPrompt (`WithSystemPrompt`)
- Provide a `core.Emitter` to receive structured events from the loop (`WithEmitter`)
- Provide `WithTextDeltaHandler`/`WithThinkingDeltaHandler` callbacks for streaming text — `func(runnerID, text string)`; the runner tags each delta with its own id so multiplexed consumers (RPC mode) can correlate deltas per turn

System reminders (todo state, etc.) no longer flow through the runner. They
are injected each iteration by `core.Extension`s implementing
`core.BeforeIterationHook` (e.g. `internal/features/reminders`), registered
on `*core.Extensions` and passed to the runner via `runner.WithExtensions`.
`harness.New` wires the default extension set — reminders, skills
(`skills.Ext`), blackboard (`blackboard.Ext`, unless disabled), and subagents
(`subagent.SpawnExt`, when depth > 0) — then appends caller extensions from
`harness.WithExtension` (also re-exported as `tenzing.WithExtension` with the
`Extension`/hook interfaces and `ToolSpec`).

Don't modify the loop. Don't add fields to the `AgentRunner` struct. Configure via `runner.AgentRunnerOption`.

## FSM Rules

Six states, six transitions. Don't add states or transitions without updating `SYSTEM_ARCHITECTURE.md`.

The FSM lives in `internal/core/fsm.go` and is per-Loop instance — subagents and concurrent loops don't share state. `TransitionStates` applies transitions with cancellation stripped from the context (`context.WithoutCancel`) — a transition abandoned mid-flight by a dead context leaves looplab/fsm's pending transition set and wedges every later transition, including the loop's terminal reset. Cancellation is classified once at the end of `Loop.run`: `errors.Is(loopErr, context.Canceled)` returns `turn canceled` with no `ErrorEvent` (a deadline stays a failure).

## Testing

- Table-driven tests as standard pattern
- Test files live next to source
- Use `testutil_test.go` for shared helpers within a package
- Mock via interfaces, not concrete types
- `go test -race ./...` catches concurrency bugs — run before any change touching goroutines, channels, or shared state

## Common Mistakes to Avoid

- **Mutating the loop.** New capabilities = new tools or new config, never loop changes
- **Importing upward.** Tools → harness or agent → runner = architecture violation
- **Wide interfaces in tools.** Tools accept narrow interfaces, not concrete types
- **Hardcoding provider behavior.** All provider differences stay in the provider layer; canonical types above
- **Forgetting `SYSTEM_ARCHITECTURE.md`.** If your change affects harness structure, agent interface, tool system, provider layer, or config surface — update the architecture doc in the same PR
